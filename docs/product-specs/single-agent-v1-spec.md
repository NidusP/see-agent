# 单智能体 V1 产品规格

## 文档控制

- 状态：活动规格
- 版本：`v1.2`
- 更新日期：`2026-07-20`
- 范围：仅限单智能体产品
- 不在范围内：平台化、代码初始化、多智能体编排

## 1. 问题陈述

业务需要一个私有部署的 AI 问答产品，能够基于内部文档回答问题，同时不将知识发送到私有环境之外。系统还必须支持持续更新知识库，并支持对智能体行为与模型配置进行受控调整。

## 2. 产品目标

交付一个基于 Web 的单智能体助手，具备以下能力：

- 基于内部知识源进行回答
- 为有依据的回答展示引用来源，并将可验证的证据锚点直接呈现在对应结论上
- 支持增量上传知识
- 支持更新提示词、风格和模型配置
- 通过配置快照保证既有会话行为稳定可复现
- 通过知识 revision、snapshot 与更新日历管理持续变化的知识，并使回答时效可解释

## 3. 成功标准

当满足以下条件时，V1 版本视为成功：

- 用户可以在 Web 界面中提问，并收到带来源的回答；有精确证据锚点时可直接查看该结论的依据
- 管理员可以上传受支持的知识文件，并看到其进入检索语料库
- 管理员可以在不重新部署代码的情况下调整提示词、语气风格和模型参数
- 产品具备最小内部登录能力，并区分普通用户与管理员入口
- 新会话使用最新配置，既有会话保持可复现
- 团队可以运行可重复的评测，对检索质量和回答质量进行比较
- 用户可以知道一条历史回答基于何时的知识，并可在知识更新后使用最新资料核验

## 4. 产品原则

1. 先保证有依据，再追求流畅
   - 检索质量和引用质量优先于表达上的润色。
2. 先做 RAG，再考虑微调
   - 产品以检索作为主要知识注入机制。
3. 可配置，但必须可复现
   - 允许运行时变更，但每个会话都必须保留创建时使用的配置快照。
4. 默认私有
   - 架构假设内部文档始终留在私有部署边界内。
5. 评测驱动迭代
   - 提示词或模型变更必须通过持久化评测 harness 进行度量。
6. 模型可替换，业务上下文不可丢
   - LLM 提供通用推理能力；产品可靠性主要来自知识、用户与任务上下文、工具、权限约束和评测闭环。
   - 专家能力通过 RAG、文档、数据库、结构化业务状态和可验证引用持续注入，而不是依赖单一模型记忆。

## 5. 用户与角色

### 5.1 知识库管理员

可以：

- 登录管理工作台
- 上传和删除知识文件
- 触发重新索引
- 创建、审核和运行新知识 onboarding 验收
- 上传和索引完成后等待系统管理员确认发布 successor snapshot

### 5.2 系统管理员

可以：

- 拥有知识库管理员全部能力
- 审核并发布 ready revision，使其进入新的知识 snapshot
- 管理智能体提示词、风格、模型与检索参数候选
- 查看全局 execution/eval evidence、组织 Q1 对照实验
- 在评测通过后审批发布或回滚参数配置
- 只有在新知识 snapshot 已通过 onboarding 后，才能停用/删除旧知识；系统必须在产品端解释未满足的阻塞条件

### 5.3 终端用户

可以：

- 登录聊天工作台
- 打开 Web 聊天界面
- 创建并继续会话
- 提出领域问题
- 查看回答来源
- 在后续版本中可选地提交回答质量反馈

V1 角色冻结为 `user`、`knowledge_admin` 与 `system_admin`。普通用户只能进入聊天；知识库管理员进入聊天和知识库；系统管理员在 Web 交互上只进入配置与质量运营。系统管理员仍保留安全发布/退役的 Backend authority，直到这些审批动作迁入配置台。部门级权限、按文件授权、跨租户隔离、用户管理 UI 和复杂审批流不进入首版门槛。

普通用户与管理员使用分离的前端登录入口：`/login` 只呈现终端用户登录体验，不显示管理员角色、凭据或能力；`/admin/login` 是知识库管理员与系统管理员共用的受控入口。两者均调用同一 Backend login/session API，Backend 返回的身份和角色仍是唯一授权依据；入口分离不构成也不替代权限校验。

## 6. 支持的输入

V1 必须支持：

- 纯文本：`txt`
- Markdown：`md`
- 结构化数据：`json`
- PDF：`pdf`
- Microsoft Word：`docx`
- Microsoft Excel：`xlsx`
- Microsoft PowerPoint：`pptx`

为控制实现复杂度，V1 首批交付仅将 Office 范围冻结为 OOXML 格式：`docx`、`xlsx`、`pptx`。遗留二进制格式 `doc`、`xls`、`ppt` 可在后续版本通过服务端转换流程补充，不作为首批上线门槛。

## 7. 核心用户旅程

### 7.1 提问

1. 用户打开产品入口。
2. 用户完成内部登录。
3. 系统进入聊天页面。
4. 用户开始一个会话。
5. 用户提出问题。
6. 系统检索相关知识。
7. 系统生成带来源的回答。
8. 用户阅读答案及其来源引用。

### 7.2 上传知识

1. 管理员上传一个或多个文件。
2. 系统存储原始文件。
3. 系统异步解析文件。
4. 系统将内容切块并建立索引。
5. 管理员查看索引状态和按文件粒度展示的结果详情。

### 7.3 更新智能体配置

1. 管理员编辑系统提示词、回答风格或模型参数。
2. 系统对配置进行版本化。
3. 新会话使用更新后的版本。
4. 既有会话继续使用其原始快照。

### 7.4 更新知识与核验历史回答

1. 管理员上传新的文档或既有文档的新 revision。
2. 系统解析、索引并在成功后发布新的知识 snapshot。
3. 更新日历记录该 revision 的发布、生效和可见性变化。
4. 后续新问题默认检索最新已发布 snapshot。
5. 用户查看旧回答或请求核验时，系统显示原回答的知识时点，并用最新 snapshot 生成独立的核验结果。

## 8. 功能需求

### 8.1 用户聊天体验

- 产品必须提供内部登录入口。
- 产品必须提供 Web 聊天界面。
- 系统必须支持流式回答。
- 系统必须持久化会话历史。
- 系统必须为每条助手回答展示来源；当回答带有可验证的证据锚点时，必须将锚点与对应来源关联展示，不能由前端猜测或伪造。
- 聊天界面必须提供可收缩的会话历史侧栏；普通用户只看聊天能力，管理员通过顶栏工作区菜单进入知识库与配置。
- 已登录工作区必须使用固定视口壳层：页面根节点不随聊天、知识库或配置内容增长而滚动，阅读区、会话列表和管理员详情等内容只在各自已声明的内部区域滚动；窄屏也必须保留单一、明确的内容滚动区。
- 聊天阅读列必须保留稳定的横向留白；默认消息视图以用户问题、助手正文和来源入口为主。完成态不得为每条消息重复展示投递状态、时间或原始 snapshot 字段；生成、失败和停止等需要用户处理的状态必须明确可见，snapshot、revision、freshness 与历史核验仍必须在按需来源详情或回答信息中可访问。
- 聊天发送操作必须置于多行输入框内，保留可访问名称、`Enter` 发送、`Shift+Enter` 换行、发送中不可并发提交以及停止/重试能力。
- 产品必须提供可扩展的界面主题注册与选择能力；主题是当前浏览器的个人显示偏好，不能改变知识、答案、角色、Agent 配置或发布状态。首版应提供一个以动植物与环保理念为灵感、同时保持阅读可访问性的主题。
- 回答内锚点的 hover/focus 必须提供轻量来源预览；用户显式点击锚点或来源入口后，系统必须在可关闭的详情抽屉展示过滤后的引用与其 provenance。
- 系统应该支持复制回答文本和查看来源详情。

### 8.2 知识库管理

- 只有知识库管理员或系统管理员可以进入知识库页面和调用知识库管理接口；只有系统管理员可以确认 `ready` revision 的发布。知识库管理员上传/索引后不得自行改变 active snapshot。
- 管理员必须能够上传文件。
- 管理员必须能够查看文件状态。
- 系统管理员必须能够在已通过新知识 onboarding 的前提下停用/删除旧文件；系统不得仅凭 UI 隐藏或文件名判断，而必须由 Backend/Postgres 在写入 transaction 中验证 replacement snapshot 与 passing run。
- 管理员必须能够对单个文件重新索引。
- 系统必须支持增量索引，而不是每次更新都要求全量重建。
- 系统必须将逻辑文档与不可变 revision 区分开，并记录 revision 的发布、生效、禁用和删除事件。
- 系统必须仅在完整索引成功后发布新知识 snapshot；失败 revision 不得影响当前可回答知识。

### 8.3 智能体配置

- 只有系统管理员可以进入配置页面和调用配置管理接口。
- 系统管理员必须能够设置：
  - system prompt
  - style guidance
  - model name
  - temperature
  - top_p
  - max output tokens
  - retrieval parameters
- 系统必须对所有配置变更进行版本化。
- 配置工作台必须以管理员可理解的语言说明每项 generation/retrieval 参数的作用、风险和当前发布状态；尤其应说明知识 snapshot 限制可回答范围、证据边界决定何时拒答、模型采样参数只影响表达而不创造知识事实。说明必须包含同一问题在不同风格、采样、输出长度、候选证据数量和证据边界下的简短回答差异示例；示例只解释可能变化，不得把某个数值写成通用最优值或绕开受控评测。
- 除非未来专门设计显式迁移动作，否则配置变更只应用于新会话。
- 每个已声明为可配置的 generation/retrieval 字段必须实际进入对应 Runtime stage，并与其版本一起记录；未实现的检索能力不得伪装为已生效。
- 配置页面必须以中文说明每项参数的作用和边界：`model_id` 不会补齐未上传知识；prompt/style 与 `temperature`/`top_p`/output budget 只影响证据表达方式、随机性或长度；`embedding_model` 变更要求独立 collection/reindex；`top_k` 是候选证据数量而非可信度；rerank 是独立排序实验；候选配置保存不是发布。
- `evidence_min_score` 必须明确说明为“最佳证据低于该边界时，Runtime 在生成前拒答”的 immutable retrieval config 字段。它只可在相同 embedding model、collection、index/chunk、strategy、scope 与相似度定义下比较；变更这些条件或知识分布后必须重新评测，不能把某个阈值复制为通用安全数字。
- 检索实现必须通过受控、版本化的 `retrieval_strategy` 选择；管理员只能选择产品已注册的策略，Runtime 只执行本地受审计实现。请求策略与 Runtime active profile 不匹配或策略未知时必须明确失败，不能按请求动态加载代码或回退另一策略。
- 当管理员选择 native embedding model 时，系统必须在摄取和查询两侧使用同一模型，并拒绝 embedding model、向量维度或索引 collection 不兼容的运行配置；不得用词法或全量检索静默替代。
- 产品完成受控 dense cutover 后，生产知识问答必须只使用已选 native dense profile；lexical 不得作为单请求 fallback。lexical 的最终删除必须在 reindex/publish、既有会话/历史核验兼容和回滚验收完成后，作为独立迁移执行；不得改写历史回答或 provenance。

### 8.4 检索、有限交流与回答

- 系统必须先区分高置信度的有限普通交流与知识问题；知识问题必须在回答生成前从已索引知识中检索，未知或混合输入默认按知识问题处理。
- 系统必须先由模型在有界会话历史内解析用户真实意图、话题关系与处置路线，再执行知识检索或简单交流回复。问候、感谢、告别、能力咨询、越界闲聊和明确公共开放世界问题可得到不使用知识库的简短受控回复；问候/能力说明必须明确“这是大模型助手，只依据已发布知识库的 RAG 检索结果回答制度、流程和业务问题”。
- 任何被模型解析为内部业务/知识问题的请求必须进入 scoped RAG；无 active snapshot、检索失败或证据不足时必须失败、澄清或如实说明不足，不能转为无引用的直接回答。模型只提出结构化 route，Backend 仍是权限、scope、route 不变量、Runtime response validation 与持久化的唯一权威；不得再用 Backend 关键词表决定普通聊天的语义 intent。
- 系统必须拒绝过度闲聊并引导回知识问答。
- 非知识回复不得显示或伪造 snapshot、freshness、citation 或“基于知识”的状态。
- 系统必须优先给出有依据的回答，并在证据不足时明确拒答。
- 系统必须在检索前以受控的有界会话上下文路由解析短追问、指代、受控交流和新话题；原始用户消息不得改写，只有经校验的 `resolved_query` 可以作为当次检索输入。明确的新话题不得被旧主题污染；无法唯一恢复的上下文依赖输入必须澄清，不得盲检索或猜测。`controlled_confirmation`、固定确认短语及其 Backend 特例不属于产品行为。
- 当内部知识请求缺少作答所必需的事项范围、对象/角色、时间版本、组织实体或排序标准，且已有对话上下文不能消除该歧义时，系统必须先提出最小且具体的澄清问题，不得以猜测补齐条件、拼凑跨事项规则或把“检索到若干片段”包装为完整答案。澄清不是拒答，也不改变该请求属于 `knowledge_query` 的事实。
- 系统必须在一条内部知识请求上区分四种可审计的回答处置：`grounded_answer`（可由证据支持的完整回答）、`clarification_required`（请求范围不足）、`insufficient_evidence`（范围已明确但没有足够证据）和 `partial_answer`（范围明确但证据仅覆盖用户要求的一部分）。`partial_answer` 必须明确说明已覆盖的范围和未能覆盖的部分，不能声称满足了用户要求的数量或比较结论。
- 澄清回复不得包含未经支持的业务事实、citation 或证据锚点；它可以记录实际发生的检索/生成观察以供管理员审计，但面向用户不得伪装为“基于知识得出的结论”。有事实结论的完整或部分回答必须继续遵守 citation 与回答内证据锚点契约。
- 已完成的知识回答必须让用户清楚区分处置：`clarification_required` 显示“需要补充范围”且没有来源入口；`insufficient_evidence` 显示“当前知识不足”且不把检索候选伪装为来源；`partial_answer` 显示“已覆盖部分”及已验证范围，只展示实际引用。Web 只能读取后端持久化处置和结构化覆盖字段，不能从正文或检索结果猜测状态；旧消息保持兼容展示。
- 系统管理员可以把已存在 execution evidence 的回答追加为质量反馈。除正确性、拒答、证据和知识演进信号外，必须能区分“本应澄清”“不应澄清”“覆盖不完整”与“引用错误”；该反馈不直接改写历史回答、知识、引用、模型参数或线上发布。
- 对 native dense 检索，系统必须将证据边界作为可版本化、可评测、可追溯的 retrieval config 事实；不得以 Runtime 内部未记录默认值决定生产拒答。
- 系统必须为引用到的 chunk 或文档附带引用信息。
- 系统必须支持以 Unicode rune 位置和 citation rank 表示回答内证据锚点；缺少或不合法锚点时保留消息级来源，不得标注为精确依据。
- 每条助手回答必须记录实际使用的知识 snapshot 与 citation revision。
- 系统必须在相关知识更新后将受影响的历史回答标记为可能过期，并提供最新知识核验能力。
- 基线设计中，系统应该支持混合检索与 reranking。

### 8.5 真实性、失败语义与运行边界

- `completed` 只表示系统真实完成了其声明的处置；它不等同于“模型已经回答”。`grounded_answer`、`partial_answer`、`clarification_required`、`insufficient_evidence` 与有限 `controlled_response` 是允许完成的处置，基础设施、契约、授权、写入或依赖错误不是。
- 没有实际 generation provider 执行，不得产生模型业务回答；没有本次 conversation 已冻结的 snapshot scope 检索，不得产生知识业务回答；没有本次实际使用的不可变 provenance，不得展示用户 citation 或证据锚点。
- Runtime、Backend 和 Web 都不得用固定文案、固定 citation、空回答替换、默认 rank/label、推测 execution facts 或空列表来伪造成功。依赖缺失、超时、契约不匹配、scope/provenance 不一致或写回失败必须显示可重试的失败或禁用能力。
- 一次聊天请求必须有可审计的 execution attempt。只有同一权威事务同时提交 assistant `completed`、正文、实际使用 citations/anchors、snapshot 与 execution evidence 时，回答才可见；失败 attempt 不得遗留 completed assistant、citation 或半成品 provenance。
- 产品运行 profile 必须显式区分 `test`、`smoke`、`fullstack_dev` 与 `production`。只有 `fullstack_dev/production` 可以声明真实 RAG；缺少 PostgreSQL、Redis、对象存储、Qdrant、实际模型 provider、服务认证或必需密钥时，必须启动失败或 not-ready，而非切换 memory/local/fake adapter。`smoke` 可以禁用知识回答，但不得伪造它。
- `/healthz` 仅表示进程 liveness；对外可用性以 `/readyz` 与受保护诊断中的实际 adapter、provider、collection、strategy、embedding identity 和 active config 一致性为准。健康端点本身不能证明模型、数据库或检索已在某次回答中执行。
- 摄取只有在解析、有效 chunk、embedding、向量投影与 manifest 校验全部成功时才可使 revision 进入 `ready`。零 chunk、扫描 PDF 而 OCR 不可用、对象存储/向量写入失败都必须是失败，不能发布 snapshot。

### 8.6 质量与治理

- 系统必须记录检索事件和生成事件日志。
- 系统必须记录每条回答的 intent，以及是否实际执行 retrieval、generation 和使用知识。
- 系统必须记录每条知识请求的回答处置、澄清所缺的范围维度（如有）以及完整/部分回答的覆盖事实；这些记录只用于可追溯、评测和管理员质量运营，不得被前端用来伪造引用。
- 系统必须为待补充的澄清记录显式生命周期，并在用户补齐范围时生成可审计的 resolved query 用于检索；resolved query 不得覆盖原始用户消息。用户另起新问题时必须放弃旧澄清，不能错误拼接上下文。
- 系统必须记录实际 generation provider、`fallback_used=false` 与 answer policy version。配置中的 `model_id` 不能单独证明该模型实际执行；generation provider 不可用时必须失败，不得生成替代回答。历史 fallback 报告不得作为真实模型质量报告或发布许可。
- 管理员必须能从一条回答查询其 message execution evidence：回答时的知识 snapshot/manifest、citation revision、agent/retrieval config、实际 retrieval/generation observation 与关联评测结果。
- 运行证据、知识 lifecycle 事件和评测报告必须持久化在私有部署的权威存储中；管理员读取不得改写历史回答、K5 provenance 或 K6 核验结果。
- 系统必须支持基于精选问题集运行离线评测。
- 管理员必须能在产品内为新知识创建和审核 onboarding 问题集：每题要么是带预期 document/revision、locator 和答案要点的 must-answer，要么是没有预期来源的 must-refuse。模型生成的问题或答案只能作为草稿，未经管理员审核不得成为评测真值。
- 管理员必须能在一个已发布 successor snapshot 上启动固定 scope 的 onboarding evaluation，并查看每题的回答/拒答、citation、locator、答案要点命中、runtime error 与总 gate verdict；该 run 必须冻结 snapshot manifest、config pair 和问题集 hash。
- onboarding evaluation 不得修改知识、参数、历史回答或 active release。它通过后才可作为“新知识已验收”的证据来退役测试 document；若同时改变 retrieval config，仍须走 Q1 approval/publish。
- 系统必须维护管理员可查询的知识更新日历与 snapshot 记录。
- 评测必须覆盖知识新增、替换、禁用、删除、未来生效与历史回答核验。
- 系统应该为后续采集用户反馈预留扩展位，以便未来扩展评测。
- 管理员必须能够将一条带 provenance 的历史回答标记为正确、错误、应拒答、证据不足/错误或知识缺口；该反馈必须保留回答当时的 snapshot、配置与 citation 证据，且不得改写历史答案。
- 管理员必须能够以固定知识 scope、数据集版本和参数条件组织候选质量实验，比较已登记的报告，并在人工审批后才将候选配置发布给新会话；单条反馈或候选配置不得自动改变线上行为。
- 发布与回滚必须留下不可变版本记录；回滚只影响后续新会话，既有 conversation 继续使用原来的 config/retrieval binding。

## 9. 非功能需求

- 仅支持私有部署
- 在会话配置层面保证回答可复现
- 对检索和生成链路具备可观测性
- 模型后端可模块化替换
- 在不造成整体停机的情况下支持增量知识更新

## 10. V1 的明确非目标

- 多智能体协作
- 带工具的工作流编排
- 外部 SaaS 连接器
- 微调管理 UI
- 完整企业级 RBAC 矩阵
- 对公网开放服务

## 11. 产品决策

### 11.1 RAG-first 决策

V1 不要求通过训练基础模型来记住知识库内容。知识通过检索注入。只有当团队通过评测证明：检索已经稳定，而回答问题主要来自表达或策略风格而非缺少证据时，才考虑微调。

### 11.2 配置快照与知识 provenance 决策

每个会话都存储并固定：

- 模型标识符
- prompt/config version
- retrieval config version

每条 assistant message 另行存储实际使用的：

- knowledge snapshot identifier 与 manifest hash
- citation 的 document/revision/chunk content hash
- answered time 与 freshness status

这样配置变更不影响既有会话的可复现性，而知识更新也不会把旧 conversation 锁死在过期知识上。普通新问题在请求开始时选择最新 published snapshot；只有回答 provenance，而不是 conversation，记录这一次选择。

### 11.3 文件格式冻结决策

V1 的必选知识输入矩阵为：

- `txt`
- `md`
- `json`
- `pdf`
- `docx`
- `xlsx`
- `pptx`

首批实现不以直接支持 `doc`、`xls`、`ppt` 为上线前提。

### 11.4 访问控制决策

V1 采用单租户、内部登录的访问模型。MVP 后端维护轻量会话 cookie，并只区分 `user` 与 `admin` 两个角色：

- 未登录用户不能访问工作台业务页面或业务 API。
- `user` 可以访问聊天页面和聊天 API。
- `admin` 可以访问聊天、知识库管理和智能体配置。
- Web 可基于角色 cookie 做导航和路由体验优化，但 Backend API 是权限判断的最终来源。
- 每个 conversation 必须绑定创建者的稳定 `owner_id`；普通用户和管理员在聊天 API 中都只能列出、读取、写入、查看来源和核验自己拥有的会话。
- 管理员的全局追溯只通过 admin evidence API 提供；管理员角色不能隐式绕过聊天资源 ownership。
- 对不存在和非本人拥有的 conversation，聊天 API 使用同一 `conversation_not_found` 语义，避免通过可枚举 ID 探测其他用户资源。

部门级权限控制、细粒度 RBAC 和跨租户隔离均延后到后续版本。

### 11.5 质量反馈与受控发布决策

管理员质量反馈、实验证据和受控发布是 V1 管理闭环的一部分；它们以 Postgres 为权威，必须锚定历史 execution evidence，不能改写知识/回答 provenance。终端用户直接反馈仍不是本切片上线门槛，后续若开放必须另行设计 conversation ownership、脱敏与审核路径。

### 11.6 引用粒度决策

V1 的引用粒度限定为文档级与结构定位级：

- 文档 / 文件名
- PDF 页码
- Word 标题路径或段落块
- Excel sheet 名称与表格 / 单元格范围
- PowerPoint 幻灯片页码

图像区域级引用、框选级证据展示和像素级定位不作为 V1 要求。

### 11.7 知识时效决策

知识不是永久不变的 conversation 属性。普通新问题使用请求开始时的最新 published knowledge snapshot；回答写入自身的 snapshot/revision provenance，用于审计和历史复放。知识更新不会改写历史 message，而是通过更新日历标记受影响回答，并在需要时创建新的核验结果。

### 11.8 会话标题决策

新建会话先以中文中性占位标题“新对话”显示。首个成功持久化的用户问题会自动生成一次标题：合并空白后截取其开头，不调用模型，也不等待或依赖模型摘要。用户可随时手动重命名；手动标题永不被自动命名覆盖。

标题命名是会话元数据，不改变 `owner_id`、配置快照、消息、知识 snapshot 或回答 provenance。后端是标题写入和 ownership 校验的唯一权威；前端不得以本地截断结果替代服务端持久化结果。历史会话标题保持不变，不做批量 AI 或文本回填。

## 12. 验收标准

当满足以下条件时，产品可进入内部试点：

- `txt`、`md`、`json`、`pdf`、`docx`、`xlsx`、`pptx` 每种类型至少有一个样例可以端到端完成上传、索引和问答
- 回答展示有效引用，并能定位到页码、标题、sheet 或 slide 等结构位置信息
- 管理员配置变更只影响新会话
- 文件删除后，被删除内容不再对检索可见
- 评测 harness 可以在同一数据集上比较至少两个模型后端
- 新 revision 发布后，新问题使用最新 snapshot；历史回答保留原始证据并可被最新知识核验
- 管理员可查看知识更新日历、snapshot 和 revision 状态

## 13. 风险

- 对图片密集型或表格密集型文档的解析质量可能低于预期。
- 如果切块忽略文档结构，检索质量可能下降。
- 如果版本化不严格，管理员侧配置变更可能引发理解混乱。
- 团队可能会在建立稳定评测基线之前过早尝试微调。

## 14. 剩余开放问题

- 是否在 V1 首批就加入 `doc`、`xls`、`ppt` 到 OOXML / PDF 的服务端转换链路？
- `xlsx` 的引用展示是否需要细化到表名和单元格范围的前端交互层？
- `pptx` 是否默认将 speaker notes 纳入检索语料，还是作为可选解析层？

- 将结构化文档视为持久化开发记录
- 相比凭直觉调整，更强调评测驱动的迭代
- 在知识 grounding 方面优先采用检索，而不是直接微调
