## 1. 决策

知识发布与上线验收解耦。系统管理员可以把已就绪的知识直接发布到当前问答快照；发布前先做测试集验收是推荐项，不是硬性前置。验收仍按现有 onboarding 规则执行：题目真值必须由管理员审核，系统不得把模型生成的内容自动当成通过证据。

停用和删除旧知识的安全门不变：没有针对相应快照的通过验收，系统管理员不能停用或删除。配置、模型、检索策略或拒答阈值变更仍走 Q1，不与内容发布混用。

实现前，现网行为保持不变：发布仍一步激活当前快照，验收只能打在已发布快照上。本文是后续实现的唯一交互与状态事实源。

## 2. 现状与问题

当前产品已经允许系统管理员在 revision 就绪后直接点「发布」。该操作在同一事务里创建后继快照并切换 active pointer，新问题会立即检索到这份知识。上线验收工作区要求填写「已发布 snapshot id」，因此只能在知识已经对用户生效之后运行。验收结果目前只硬卡停用和删除。

问题不在「能不能跳过验收」，而在缺少发布前的推荐路径，也缺少一眼可辨的发布状态。管理员无法在不切换线上知识的前提下，对「旧知识 + 新知识」的后继快照跑验收；直接发布后，界面也不区分已验收、未验收和验收未通过。

## 3. 非目标

- 不取消 onboarding，不降低 must-answer / must-refuse 的真值审核要求。
- 不让模型自问自答并自动通过。
- 不改变普通用户聊天路径，不让待发布快照进入问答检索。
- 不改变 Q1 配置发布/回滚，不把 onboarding 通过当成配置发布许可。
- 不放松停用/删除的退役安全门。
- 不在本包修改历史回答、引用或 provenance。

## 4. 角色

- 知识库管理员：上传、替换、查看状态；在待发布或已发布快照上创建、审核、冻结问题集并启动验收；可以让系统起草草稿题，但不能确认发布，也不能自行切换 active snapshot。
- 系统管理员：拥有上述能力；唯一可以激活待发布快照或直接发布的角色。直接发布时必须明确确认「尚未完成上线验收仍要发布」。停用/删除仍要求相应通过验收。
- 普通用户：只使用当前已发布快照；不参与出题、验收或发布。

## 5. 交互

revision 进入 `ready` 后，系统管理员在知识页看到「准备发布」，而不是立即弹出浏览器原生确认框。准备发布会生成待发布快照（包含旧知识与这份新 revision），不切换线上问答。

待发布面板展示：

1. 即将生效的快照成员（旧 + 新）。
2. 上线验收状态：未跑、通过、未通过。
3. 推荐动作：按新文档起草必答题和必拒题（草稿）、管理员确认、冻结、运行。
4. 主按钮与次按钮随状态变化：
   - 验收通过：主按钮为「发布已验收的知识」，无需额外声明。
   - 未跑验收或验收未通过：主按钮仍引导去验收；次按钮为「直接发布」，必须勾选「我知道尚未完成上线验收，仍要发布」后才能提交。未通过时文案要写明：发布后这份知识会立刻服务用户，但验收未通过。

发布完成后，该快照在知识页、更新日历和文档详情上显示三种状态之一：

- 已发布 · 已验收
- 已发布 · 未验收
- 已发布 · 验收未通过（仍在服务）

未验收或未通过时，知识页保留提醒，并提供「补跑验收」。补跑通过后，状态升级为已验收，不必重新发布。该提醒不阻断聊天，也不阻断继续上传。

知识库管理员在待发布阶段即可录入或确认题目并跑验收；他们看到的是「等待系统管理员发布」，而不是发布按钮。

## 6. 快照、发布与验收状态

现网快照状态机是 `building -> published -> retired`。本设计在实现时增加 `pending_publish`：

```text
snapshot: building -> pending_publish -> published -> retired
```

规则：

- 只有 Backend 可以创建待发布快照、写入成员 manifest，以及稍后把它激活为当前 published snapshot。
- `pending_publish` 不得成为 active pointer，不得被普通问答检索。`GetActivePublishedSnapshot` 只返回 pointer 指向且状态为 `published` 的快照。
- onboarding 可以针对 `pending_publish` 或 `published` 快照运行；仍不得用已 `retired` 的快照批准新知识。
- 对同一 ready revision、同一父快照和同一成员集合，重复「准备发布」返回同一待发布快照。若又出现新的 ready revision，旧的待发布快照作废为 `retired`（从未激活，不进入问答），再创建新的待发布快照。
- 「直接发布」若尚无待发布快照，允许在同一事务中创建并立即激活，但必须带有未验收确认；若已有待发布快照且已有通过验收，则按已验收路径激活，不要求该确认。
- 激活待发布快照时：将该快照改为 `published`，切换 active pointer，将此前的当前 published 快照改为 `retired`。已有问答会话仍绑定各自创建时的 snapshot scope。
- 验收状态是派生事实，不以管理员手填为准：存在针对该 snapshot 的 passing onboarding run 即为已验收；否则看最近一次完整 run，失败则为验收未通过，没有完整 run 则为未验收。发布当时要把该派生状态和（如有）run id 记入发布事件，便于审计；之后补跑通过可以更新展示状态，但不改写历史事件。

## 7. 题目起草与确认

系统可以根据待发布或已发布快照中的新 revision 起草题目，降低管理员从零出题的成本。生成结果一律为 `draft_generated`：

- 必答题：须带上建议的 document/revision、locator 提示和答案要点，并指向新知识中可核验的事实。
- 必拒题：须是当前快照不应回答的问题，且不能带预期来源。生成器不得用“回答质量不好的题目”充数。

管理员必须逐题确认或修改后，将状态改为 `reviewed`，否则不能进入冻结和运行。未审核题目不得计分，也不得作为通过证据。生成失败时，管理员仍可手工出题并直接发布（若选择跳过验收）。

最小验收门槛沿用 K8-R4a：至少一条已审核必答题、至少三条已审核必拒题，全部通过且无 runtime error。本包不降低该门槛；它只决定验收是不是发布的前置条件。

## 8. API 与写入路径

实现时由 Backend/Postgres 作为唯一 writer。建议在现有 K4 管理员接口上拆出两步，而不是让 Web 自己拼快照。

| 路径 | 行为 | 关键约束 |
| --- | --- | --- |
| `POST /api/kb/revisions/{revision_id}/prepare-publish` | 创建或返回待发布快照 | 仅 `ready` revision；不切换 active pointer；幂等 |
| `POST /api/kb/snapshots/{snapshot_id}/activate` | 将 `pending_publish` 快照激活为当前知识 | 仅系统管理员；无 passing run 时必须带未验收确认；有 passing run 时不得再要求该确认 |
| `POST /api/kb/revisions/{revision_id}/publish` | 保留为兼容入口 | 无待发布快照且无 passing run 时，等同「准备 + 直接激活」，必须带未验收确认；不得再只靠浏览器 `confirm()` |

现有 onboarding API 继续使用，但创建问题集与启动 run 必须接受 `pending_publish` 快照。题目草稿生成若新增接口，也必须是管理员接口，带 `Idempotency-Key`；生成器只写 draft case，不能 freeze，不能启动 run，不能发布或删除知识。

Web 只展示服务端状态。待发布、已验收、未验收、验收未通过和退役阻塞原因都以后端返回为准。

## 9. 退役与配置发布

- 停用：系统管理员只能在「旧 + 新」的当前 published 快照取得 passing onboarding run，且 readiness 为 `ready_to_disable` 后执行。Backend/Postgres 在同一事务中复核，界面不能绕过。
- 删除：只能删除已停用文档，且须在不含旧知识的当前快照再次取得 passing run、readiness 为 `ready_to_delete`。
- 直接发布或验收未通过就发布，都不构成退役许可。
- 若发布时同时要切换检索策略、embedding、索引或拒答阈值，仍先走 Q1；本包只覆盖知识内容发布。

## 10. 验收标准

实现本设计后，至少覆盖：

- 准备发布后，active snapshot 不变，普通聊天仍检索旧的 published 快照。
- 待发布快照可创建、审核、冻结并运行 onboarding；retired 快照仍不能用于批准新知识。
- 验收通过后，系统管理员一键激活，新问题检索新快照，发布状态为已验收。
- 未跑或未通过时，无确认不能激活；有确认可以激活，状态分别为未验收、验收未通过（仍在服务），聊天不被阻断。
- 发布后补跑通过，展示状态变为已验收，不必重新发布，历史发布事件保留当时状态。
- 没有相应 passing run 时，停用/删除仍然失败，并返回可展示的阻塞原因。
- 草稿题未经审核不能冻结；生成失败不影响手工出题和直接发布。
- 现有 K4 idempotency、K5 会话 scope、K7 evidence、Q1 与退役门禁不回归。

## 11. 回滚

- 只创建了待发布快照、尚未激活：丢弃或 retire 该快照即可，线上知识不变。
- 已直接发布但验收未通过：保留该 published 快照为当前知识；修复文档或索引后上传新 revision，重新走准备发布与验收。不要用数据库 reset 回退。若必须撤下新知识，按现有退役门禁处理，不得在无通过验收时强行删除最后一个有效文档。
- 代码回滚：未实现本设计前的一步发布入口必须保持可运行；实现后若回退代码，不得留下聊天可检索、状态却不是 `published` 的快照。

## 12. 实现顺序

1. 先更新本文、产品规格与相关设计/runbook（本步骤，不改服务代码）。
2. Backend：`pending_publish`、准备发布、激活、发布事件中的验收状态、onboarding 接受待发布快照。
3. Web：用待发布面板替换原生 `confirm`，展示三种发布状态，接入草稿出题与补跑验收。
4. 测试：补发布前验收、直接发布确认、聊天不看到待发布快照、退役门禁仍生效的证据。
5. 未经用户明确授权，不提交、不推送、不发布。
