# see-agent 接入 LangChain 与 LangGraph 的改造设计

状态：设计，未实现。
日期：2026-10-22。
范围：Python AI Runtime 的提问路径。不改产品边界，不把本系统改成制造业项目。

本文说的 LangChain，是把模型、提示词、检索器和输出解析接在一起的组件库。LangGraph 是在这些组件外面画一张可循环的状态图。RAG（检索增强生成）指先从已发布知识里查出片段，再让模型基于这些片段回答。

## 1. 结论

see-agent 不整仓换成 LangChain 应用。Web、Go Backend、PostgreSQL、Redis、MinIO、Qdrant 的职责保持不变。LangChain 只替换 Python 运行时里「检索、提示词、模型调用、结构化输出」这几块可替换零件。LangGraph 只接管一次提问的控制流：意图判断、检索、证据是否够用、最多重写一次问题、生成或明确失败。

现有失败即关闭（fail-closed，模型或检索不可用时不编造成功回答）、知识快照、引用回溯和评测门槛继续有效。LangGraph 的检查点不是会话真相。会话仍由 Go 写入 PostgreSQL，并按用户归属隔离。

## 2. 现在的系统

一次用户提问的路径是：

1. Next.js 只做登录、会话和流式展示。
2. Go Backend 校验身份，确定这次提问能看见的知识快照，把请求交给 Python 运行时，并把回答、引用和执行记录存进 PostgreSQL。
3. Python 运行时的 ChatPipeline 组织这次提问。RetrievalPipeline 在指定快照内做向量检索。answer_pipeline.py 里的回答策略决定是回答、澄清，还是证据不足。model_client.py 调用本地 Ollama。api/chat.py 把结果编成 SSE（服务端推送的事件流）。

文档摄取是另一条路：解析、切分、嵌入，写入 MinIO 和 Qdrant。它不在这次图的循环里。管理员发布快照之后，提问才能看见新文档。

因此当前产品已经是一条 RAG 链，还不是会自己挑工具、循环执行的智能体。改造要补的是控制流，不是再做一个知识库。

## 3. 不做什么

- 不用 LangChain 的默认对话记忆替换 PostgreSQL 里的会话。否则一份对话会有两个主人。
- 不用 LangGraph 的默认检查点数据库保存用户可见历史。图的检查点只表示这一次提问走到了哪。
- 不把 Qdrant 查询改成全库相似搜索。检索必须继续带上已发布快照和修订范围，否则回答会串到未发布或已停用的文档。
- 不让模型自由调用 shell、任意 HTTP 或写数据库。第一期没有开放工具循环。
- 不把 Go 的身份、发布事务和证据接口重写成 Python。
- 不在评测通过前把新图设为默认路径。旧的 ChatPipeline 保留到切换完成。

## 4. 两层分别负责什么

LangChain 负责无状态零件，放在 services/ai-runtime-py/app/adapters/ 和现有 pipeline 后面：

- 嵌入和 Qdrant 检索器。检索器必须接受调用方传入的快照过滤条件，不能在组件内部决定能看见哪些文档。
- 对话提示词模板。模板文本仍以仓库里的版本化提示词为准，不把提示词散落在图节点的字符串里。
- 聊天模型适配。继续面向现在的 Ollama 配置，失败时抛出已有的模型错误，不在适配器里返回兜底回答。
- 结构化输出解析。回答策略已经要求模型给出可判断的依据。解析失败视为这次生成失败，而不是当成一段普通回答展示。

LangGraph 负责有状态的一次提问，新增 app/graphs/chat_turn.py。图的输入是 Go 已经授权好的请求，输出仍是现在的 ChatResponse 和 ChatStreamEvent，这样 Web 和 Go 不用同时改协议。

## 5. 提问图

接收已授权请求之后先做意图判断。非知识闲聊走固定短回复，不检索，也不调用模型。知识问题按快照检索。证据够用就按现有策略生成，再核对引用是否对应检索片段；对应则流式输出回答和引用。证据不够且还能重写一次，就改写问题并回到检索。第二次仍不够，或者模型、检索失败，或者引用对不上片段，就明确失败，并保留这次执行记录。

重写问题最多一次。第二次证据仍不够，就走失败，不再循环。这个上限写在图的状态里，不靠提示词自觉停止。

意图判断沿用现在已经验证过的有限交流规则：问候可以短回复；开放闲聊引导回知识问答；夹带业务内容的问题继续走检索。不要用一个自由分类器替换这组规则。

## 6. 图的状态

一次提问在图里只带这些字段：

- 原始问题和改写后的问题，以及已经重写的次数。
- Go 传来的快照、修订范围、检索策略和模型配置。这些字段图只能读，不能改。
- 检索候选、分数和引用标识。
- 意图结果：知识问答，或固定短回复。
- 终态：回答、澄清、证据不足、模型失败、检索失败。
- 给现有 SSE 用的事件。生成节点之前不产生假的正文增量。

不把 API 密钥、数据库连接串或完整对象存储路径放进图状态。日志只记终态、耗时和错误类别，不记文档原文。

## 7. 和现有代码的对应

- pipelines/chat_pipeline.py 的 ChatPipeline：保留为入口。增加一个开关，决定走旧链还是新图。默认仍是旧链。
- pipelines/retrieval_pipeline.py 的 RetrievalPipeline：继续拥有快照过滤。LangChain 检索器只是它内部的一种实现。
- pipelines/answer_pipeline.py：生成、引用核对、证据不足和澄清仍走这里。图节点调用它，不复制一套策略。
- adapters/model_client.py：包一层 LangChain 模型接口。错误类型保持为现在的 ModelClientError。
- adapters/embeddings.py 和 adapters/vector_store.py：同上，Qdrant 过滤条件由检索管道传入。
- api/chat.py：对外仍是现在的请求和 SSE。图的内部事件先翻译成现有 ChatStreamEvent。
- 摄取管道 ingestion_pipeline.py：第一期不改。切分和嵌入可以在后续用 LangChain 文档组件替换，但发布事务仍在 Go。

开关使用显式配置，只在运行时配置里打开新图。未打开时，现有测试的请求和响应必须不变。

## 8. 分三期

### 第一期：零件对齐，行为不变

在检索、嵌入、模型调用外面加 LangChain 适配，默认不启用。用现有运行时测试比较旧实现和新适配：同一份快照、同一个问题，引用标识和失败类别一致。流式输出仍由现有 SSE 发出。

完成标准：现有检索、回答策略、引用锚点和健康检查测试通过。新适配失败时，入口可以切回旧实现。

### 第二期：启用提问图

把第 5 节的图接到 ChatPipeline，默认仍关闭。打开后只多做两件事：证据不足时最多改写一次问题再检索；第二次仍不足，或引用对不上检索片段，就失败。

完成标准：

- 问候不触发检索，也不调用生成模型。
- 快照之外的文档不会被检索到。
- 检索或模型失败时，界面收到失败，PostgreSQL 里留有这次执行记录，没有一段看起来答完的正文。
- 重写次数不会超过一次。可以用固定输入看到状态里的计数。
- 同一组评测题在打开新图后，不允许为了通过而降低现有回答、引用和拒答门槛。

### 第三期：只读工具，仍不开放自由代理

如果第二期稳定，再增加由服务端注册的只读工具，例如按已授权快照读取文档元数据、查看知识是否过期。工具名单写死在运行时里。模型不能临时注册工具，也不能决定工具的权限。写操作，包括发布、停用、删除，仍只能走 Go 的管理员接口。

完成标准：工具调用记录进执行证据；越权快照被拒绝；评测门槛不下降。

## 9. 依赖和部署

Python 运行时增加 LangChain 与 LangGraph 依赖时，要钉住版本，和现在的 FastAPI、httpx 一起放进 requirements.txt。本地仍用现有 Docker Compose 启动 PostgreSQL、Redis、MinIO、Qdrant 和 Ollama。不新增数据库，不把向量库换成框架自带的临时存储。

升级框架版本时，先跑第一期的对比测试，再考虑打开新图。框架默认参数，尤其是检索条数、重试和记忆，不能覆盖 see-agent 已经冻结的快照和失败语义。

## 10. 风险

- 框架自带的代理循环会把「检索不到」修成一段流畅回答。图的失败节点必须在代码里返回失败，不能只在提示词里要求模型诚实。
- 重写问题可能逐步偏离用户原意。所以只允许一次，并且界面和执行记录要能看出回答依据的是原问题还是改写后的问题。
- 两套实现并存会分叉。旧链只留到第二期评测通过并默认切换之后，然后删除旧的提问编排，而不是长期双写。
- LangChain 的检索器如果忽略过滤条件，会造成跨快照串读。第一期测试要专门构造「未发布文档更相似」的例子，确认它不会被选中。

## 11. 验收顺序

1. 先读本文，确认不搬动 Go、PostgreSQL 和发布事务。
2. 实现第一期适配，但不打开新图。
3. 用现有评测和失败用例对比旧链与新适配。
4. 再实现第二期的图，并单独打开开关验收。
5. 门槛不下降后，才把新图设为默认，并删除旧的提问编排。
